# pesajes module

Specs: 03, 04 (derived quality state), 10 (annulment), 15 (history), 16 (filters), 19 (approver review), 21 (`GET /pesajes/:id`), 29 (pagination), 38 (supervisor PIN), 44 (observations), 47 (destination of an approver-rejected weigh-in). Eight routes.

## Access control

`createPesaje` validates `cliente_operador` (the `cliente_id` is resolved from the lote). Everything else skips it, by decision: `PATCH /pesajes/:id/rechazar`, both `byApprover` reviews, `GET /pesajes/:id`, `GET /pesajes/byLote/:loteId` and `POST /pesajes/validar-pin`. `GET /pesajes/:id` is the cheapest open read in the project to walk: `pesajes.id` is sequential, so incrementing a number reaches every weigh-in. **`GET /pesajes/historial` is not one of them**: it filters by the caller's own `usuario_id` and there is nothing to authorize.

## `pesajes` columns

`peso_bruto`/`tara`/`peso_neto` (decimals come back as `string | number`), `fuera_de_rango`, `estado_calidad_id`, `lote_id` (nullable), `usuario_id`, `id` (a `BIGINT`, `Generated<string | number>` — coerce with `Number()`).
- `isActive` + rejection trio `motivo_rechazo`/`rechazado_por`/`rechazado_en` — the **operator's annulment** (`PATCH /pesajes/:id/rechazar`), which hides the row from both listings.
- `aprobado`/`aprobado_por`/`aprobado_en` — the **approver's review**, added by hand outside any spec and adopted by spec 19. **`aprobado` is tri-state**: `1` approved, `0` rejected by the approver, `NULL` nobody reviewed it. Typed `boolean | null`, but MySQL returns `0`/`1`: **compare by truthiness or against `null`, never with `=== false`**. Reads map it with `p.aprobado === null ? null : !!p.aprobado`. `aprobado = 0` is a different concept from `isActive = 0`: the row **stays active and visible**.
- `aprobado_con_excepcion_por INT NULL` (spec 38, FK → `usuarios`) — the supervisor who authorized an over-maximum weigh-in. No `_en`: the date is `autorizaciones_pin.usada_en`, joined by `pesaje_id`. Not the approver's `aprobado_por`.
- `destino_id INT NULL` (spec 47, FK `fk_pesajes_destino` → `destinos`, right after `rechazado_en`) — where the product the **approver** rejected goes (local market, waste…). Written only by `PATCH /pesajes/:id/rechazar/byApprover`, where it is mandatory; `NULL` on every other row (unreviewed, approved, annulled by the operator, rejected before spec 47). The obligation lives in the DTO, not in MySQL. `destinos` (`id`, `nombre`, `isActive`, `created_at`, **no `codigo`** — the id is the identity, by decision) is hand-maintained: no CRUD, rows inserted in MySQL, `db/seed.sql` seeds `MERCADO LOCAL` (1) and `DESECHO` (2). Selector: `GET /catalogos/destinos`.
- `observaciones VARCHAR(500) NULL` (spec 44) — the operator's free-text note (°Brix, pulp temperature…), the deliberately unstructured stand-in for measurements nobody has asked to model. Written only by `POST /pesajes`, never edited, returned by the three reads — and **not** by chat, the summary or metrics, by decision: free text may carry anything and sending it to Google is its own spec.
- **No read returns** `aprobado_por`, `aprobado_en`, `rechazado_por`, `rechazado_en`, `destino_id` or `aprobado_con_excepcion_por` — nor do chat, the AI summary or metrics read `destino_id`. `motivo_rechazo` is readable only inside the text of `GET /pesajes/:id`'s 400.

`estados_calidad`: the quality states, resolved by `codigo` (`resolveEstadoCalidad`); no `isActive`. `POST /pesajes` derives the state from the weight against the lote's bands.

## Filter convention (spec 16) — the reference for every filter in the project

1. **No filter can ever produce a 400.** Every field is `.optional().catch(undefined)`; a malformed, empty or unknown param is ignored and the query runs without it. Recorded risk: a front typo returns a list that looks filtered and is not. (`FiltrosClientesDto` and spec 35's metrics break this rule.)
2. **Filtering never widens a result**, only narrows it.
3. **`GET /pesajes/historial` does not accept `?usuario_id`, by design.** Spec 15's whole guarantee is that the endpoint has nowhere to write another user's id; Zod drops the key. Do not add it "for symmetry with `byLote`" — `byLote` has it because that route already returns every operator's weigh-ins. (Spec 35's metrics have one; no contradiction, that route never promised "only yours".)
4. **Booleans travel as `true`/`false`** and the DTO's `.transform()` converts them to `tinyint`, never the repository. `?fuera_de_rango=1` does **not** filter, although the response returns `0`/`1` — the likeliest tripwire. The DTOs still accept both forms (`z.union([z.enum(['true','false']).transform(...), z.union([z.literal(0), z.literal(1)])])`), a workaround from the double pipe; unnecessary now but harmless.
5. **Ids filter the base-table column** (`pesajes.estado_calidad_id`, not `estados_calidad.id`), so filters never depend on a join. But filtering a `LEFT JOIN`ed column (`?nombre`, `?cliente_id` in `historial`) drops orphan rows.
6. `desde`/`hasta` are `fechaISO().optional().catch(undefined)` on `created_at`, `hasta` **inclusive** of the whole day (`DATE_ADD(hasta, INTERVAL 1 DAY)`).

## Routes

**`POST /pesajes`** — one weigh-in per request; the backend computes `peso_neto = peso_bruto - tara`, `fuera_de_rango` and `estado_calidad_id` (the body accepts none of them). Requires an open lote (`validateLoteAbierto`), so no weighing happens after approval. Response `{ id, peso_neto, fuera_de_rango }`.
- Optional **`autorizacion_token`** (a UUID, Zod 400 otherwise) from `POST /pesajes/validar-pin`. **The backend does not block**: an over-maximum weigh-in without a token is saved as before, with `aprobado_con_excepcion_por = NULL` — the PIN lock lives in the front, by decision. With a token **and** `peso_neto > peso_maximo` (strict; equal is `IDEAL`), it reads the authorization `FOR UPDATE` after every other validator passes, answers **400** `La autorizacion no existe` / `La autorizacion ya fue utilizada` and saves nothing, or writes `aprobado_con_excepcion_por = supervisor_id` and marks the authorization used (`usada_por`, `usada_en = NOW()`, `pesaje_id`) in the same transaction. With any other weight the token is **ignored and not consumed**. The state stays `MAXIMO` and `fuera_de_rango` stays `1` either way.
- Optional **`observaciones`**: trimmed **before** measuring, capped at **500** (**400** `Las observaciones no pueden superar los 500 caracteres`); a non-string is a 400; empty, blank or `null` is saved as `NULL` with no error (unlike spec 41, which 400s on an empty string).

**`POST /pesajes/validar-pin`** (spec 38) — first half of the PIN flow. Body `{ pin }` (`/^\d{4}$/`, 400 `El PIN debe tener 4 digitos`). **The PIN is the supervisor's identity** — no name selector. Looked up in `pines_supervisor` joined to `usuarios` and `roles`, demanding `roles.nombre = 'SUPERVISOR'` and `isActive` not `0`; any miss answers the **same 400** `PIN incorrecto` (400 and not 401, so the front does not think the session expired). On a hit inserts an `autorizaciones_pin` row and answers **200** (`@HttpCode(200)`) `{ ok, msg, autorizacion: { token, supervisor } }`, `supervisor` being `complete_name`. **No attempt limit** and a 400 is not logged: brute forcing 10.000 PINs leaves no trace — an accepted risk.

**`autorizaciones_pin`** — one row per successful `validar-pin`: `token CHAR(36)` (`crypto.randomUUID()`, never the sequential id), `supervisor_id`, `solicitado_por`, `created_at`, and `usada_por`/`usada_en`/`pesaje_id`, `NULL` until consumed (`usada_en IS NOT NULL` = used). `UNIQUE (token)` and `UNIQUE (pesaje_id)`. The authorization **never expires and is bound to nothing** (not the operator, the lote or the weight), serves once, and the supervisor's role and `isActive` are **not** re-checked at consumption. `pesaje_id` is `BIGINT` to match `pesajes.id`. A weigh-in with `fuera_de_rango = 1`, state `MAXIMO` and `aprobado_con_excepcion_por = NULL` saved after spec 38 went around the PIN.

**`GET /pesajes/byLote/:loteId`** — weigh-ins of one lote, quality state and user resolved by join, `isActive = 1`, `created_at` DESC. **22** fields, `observaciones` last (`null` when absent). Six optional filters: `usuario_id`, `estado_calidad_id`, `fuera_de_rango`, `nombre` (`LIKE` on `usuarios.complete_name`), `desde`, `hasta`. `lote_id` and `isActive = 1` always apply.

**`GET /pesajes/historial`** (spec 15) — the caller's own history. **The filter is the token** (`pesajes.usuario_id = req.user.userId`). **Sixteen** fields: the `byLote` ones minus `usuario`, plus `nombre_lote`, `cliente` and `unidad_medida`, with `observaciones` last. **Four `LEFT JOIN`s**, so a pesaje with null `lote_id` comes back with those three null. Deliberately **no** `lotes.estado`, `clientes.isActive` or `cliente_operador` filter: the only endpoint that returns the `nombre_lote` of a closed lote and the `nombre` of a rejected client, and an operator unlinked from a client keeps seeing what they weighed for it. Seven optional filters: `lote_id`, `cliente_id` (on `lotes.cliente_id`), `estado_calidad_id`, `fuera_de_rango`, `nombre` (`LIKE` on `lotes.nombre_lote`, not on `clientes.nombre`), `desde`, `hasta` — **no `usuario_id`**. Optional pagination (spec 29). Never 404 and never 400: a token whose user no longer exists gets 200 with `[]`.

**`PATCH /pesajes/:id/rechazar`** (spec 10) — the operator's **logical annulment**, not the `RECHAZADO` quality state: `isActive = 0` plus the rejection trio; weights and `estado_calidad_id` untouched. Body `motivo`, 5–255; `{ ok, msg }`. 400 if the pesaje does not exist, is already rejected, has a null `lote_id`, or its lote is not open. Irreversible; no endpoint lists annulled weigh-ins.

**`PATCH /pesajes/:id/rechazar/byApprover`** — the approver's "no": `aprobado = 0` plus the rejection trio and `destino_id`, in one `UPDATE`, and **`isActive` stays `1`**, so the row stays visible with `aprobado: false`. Body (`RechazarPesajeAprobadorDto`, its own DTO so the operator's annulment is untouched): `motivo`, 5–255, and **`destino_id`, a mandatory positive integer** — Zod 400 if missing or not a number (Zod's default English message, kept by decision), `El destino_id debe ser un id valido` for `0`, negatives or decimals. `{ ok, msg }`. Validators in order: the pesaje does not exist, is annulled, was already reviewed, has a null `lote_id`, its lote is not a closed one in `CLIENTE_FINAL`, then `validateDestino` — **400** `El destino con id 'X' no existe` / `El destino '<nombre>' no esta activo`. With no active row in `destinos`, every approver rejection answers 400.

**`PATCH /pesajes/:id/aprobar/byApprover`** (spec 19) — the approver's "yes": writes exactly `aprobado = 1`, `aprobado_por`, `aprobado_en = NOW()` — the only writer of `aprobado = 1`, the narrowest `UPDATE`. **No body, no DTO.** `{ ok, msg }`. Does not touch the lote: approving the last unreviewed weigh-in changes nothing about it. 400 if the pesaje does not exist, is annulled (`isActive = 0`), was already reviewed (`aprobado IS NOT NULL`, one message for each verdict), has a null `lote_id`, or its lote is not closed / not in `CLIENTE_FINAL` / rejected. Irreversible.

**`GET /pesajes/:id`** (spec 21) — one weigh-in, for a QR scan (the label carries the id). Returns **exactly the 22 fields of `byLote`**, same joins, aliases, order and `TINYINT` normalisation, so it is interchangeable with one element of that array. `{ ok, msg, pesaje }`. No filter beyond the id (returns weigh-ins of closed, rejected and finalized lotes). **Three outcomes**: 200 if active; **404** `El pesaje con id 'X' no existe` (the `PATCH`es answer 400 for the same sentence — read vs write); **400** `Este pesaje no esta activo. Motivo: <motivo_rechazo>` if `isActive = 0` — the motive travels inside the message, never as a field. One query: it selects 24 columns and drops `isActive`/`motivo_rechazo` before returning. The check is `isActive === 0`, **not `!== 1`**, so a `NULL` row answers 200 while the listings hide it.

**`@Get(':id')` is declared last in `PesajesController`, after `historial` and `byLote/:loteId`, and that position is load-bearing.** Moving it up silently breaks two endpoints that still compile.

## Deferred

Weighing at `CLIENTE_FINAL`, a PIN under `peso_minimo`, an `APROBADO CON EXCEPCIÓN` state, alert severity, hashing the PIN, expiring or binding authorizations, attempt limits, generating the QR (the front's job), a QR code distinct from the primary key, batch/offline sync and device idempotency by `(dispositivo_identificador, secuencia_dispositivo)`. From spec 47: a destination on the operator's annulment or on a rejected lote, returning `destino_id`/`motivo_rechazo` in the reads, the destination in chat/summary/metrics, CRUD of `destinos`, and editing or backfilling a destination.
