# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run start:dev      # run with watch mode (default for local dev)
npm run start:debug    # watch mode + --inspect
npm run build          # nest build -> dist/
npm run start:prod     # node dist/main (run build first)

npm run lint           # eslint --fix over src/apps/libs/test
npm run format         # prettier --write over src and test

npm run test           # jest unit tests (*.spec.ts, rootDir: src)
npm run test:watch
npm run test:cov
npm run test:e2e       # jest -c ./test/jest-e2e.json
```

Run a single unit test file: `npx jest path/to/file.spec.ts`. There are currently no `*.spec.ts` files or `test/` e2e directory in the repo — testing infra is configured (jest, ts-jest, supertest) but unused so far.

Server listens on `process.env.PORT` (default 4000). No global route prefix is set (the `app.setGlobalPrefix('api/v1')` line in `src/main.ts` is commented out).

Required env vars (see `.env`, not committed): `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `JWT_SECRET`, `PORT`.

## Spec-driven workflow

This repo is developed spec-first via two local skills in `.agents/skills/` (mirrored in `.claude/skills/`):

- `/spec` — designs a spec interactively and saves it to `specs/NN-nombre.md` (template at `.agents/skills/spec/template.md`). No code is written in this phase.
- `/spec-impl <NN-spec-name>` — implements an already-approved spec, creating a git branch named after it.

`specs/` holds the source of truth for what was decided and, just as importantly, what was **deliberately deferred** (each spec has `Out of scope`, `Decisions`, `Risks` and `What is not in this spec` sections). Before adding a feature, check whether an existing spec already ruled it out and why — new work goes in a new spec rather than silently expanding an old one. Specs are written in Spanish; the codebase and this file are in English.

Existing specs (all marked `Implemented`): `01-vinculacion-cliente-operador.md`, `02-modulo-lotes.md`, `03-guardado-de-pesajes.md`.

## Architecture

NestJS API (Express platform) backed by MySQL via Kysely (no ORM, no migrations tooling checked into the repo — the DB schema is assumed to pre-exist and is only mirrored in TypeScript types).

**Request-scoped DB connection pattern** — this is the key non-obvious mechanism:
- `DatabaseMiddleware` (`src/database/middlewares/database.middleware.ts`) runs on every route (`forRoutes('*')`, wired in `DatabaseModule`), opens a new `Kysely` instance with a 1-connection `mysql2` pool per request, and stashes it on `req['db']`. The pool is destroyed when the response finishes (`res.on('finish', ...)`).
- `DatabaseService` (`src/database/database.service.ts`) is `Scope.REQUEST`-scoped and just pulls `request['db']` in its constructor via `@Inject(REQUEST)`.
- Any provider that injects `DatabaseService` becomes request-scoped too (Nest scope propagation), and repositories access the query builder through `this.dbService.client`.
- `Database` and the `*Table` interfaces in `src/database/types/types.ts` are the hand-written Kysely schema — when adding a table/column in MySQL, update this file by hand (no codegen). Note the `Database` key for units is `unidades_medida` (plural) even though the interface is `UnidadMedidaTable`; use the plural form in queries.

**Auth/guard flow:**
- `JwtAuthGuard` (`src/guards/jwt-auth.guard.ts`) is registered globally both via `APP_GUARD` in `AppModule` and again manually in `main.ts` (`app.useGlobalGuards(new JwtAuthGuard(reflector))`), so every route requires a valid JWT by default.
- Use `@Public()` (`src/decorators/public.decorator.ts`) to opt a specific route out — only `AuthController.login` and `AuthController.register` are marked `@Public()`.
- `JwtStrategy` (`src/strategy/jwt.stategy.ts`) validates the bearer token and returns `{ userId, username }`, which becomes `req.user`. Controllers read it as `const { userId } = req.user as { userId: number }`.
- Global pipes: `ZodValidationPipe` from `nestjs-zod` is registered both as `APP_PIPE` in `AppModule` and again manually in `main.ts` — DTOs are Zod schemas wrapped with `createZodDto()` (see `src/modules/*/dto/*.dto.ts`), not `class-validator`.
- Roles exist in the DB (`roles`, `usuarios.rol_id`) but **no endpoint discriminates by role yet** — every authenticated user has the same permissions.
- The `permisos` table (spec 06) declares what each role is *supposed* to be able to do. Exactly one thing reads it — `GET /permisos/me` (spec 07), which hands the caller its own role's codes so a client can hide buttons — and **nothing enforces it**: there is no `PermissionsGuard` and no `@Permisos()` decorator, `req.user` is still `{ userId, username }`, the JWT payload is unchanged (`sub`, `user_id`, `username`) and `POST /auth/login` does not return permissions. An `OPERADOR` gets a 201 from `POST /clientes` whatever the table says about it. Enforcing it is a future spec. (Spec 06's example of this — that the table denies `OPERADOR` the `clientes.crear` code — no longer holds: that code is not in the DB, and the role does hold `CREAR-CLIENTE-NUEVO`. See the spec 14 note at the end of this list.)
- Spec 08 raised the stakes of that gap. `GET /clientes/all` was declared by a `clientes.listar_todos` row seeded for `Admin` only — a row that **is no longer in the DB**, see the spec 14 note below — but nothing reads it on the request path either way — so an `Operador` calling that route gets 200 with **every** client. It is the first endpoint that opens data previously closed: until the guard lands, the `cliente_operador` filter on `GET /clientes` is bypassable by calling the route next to it.
- Spec 09's three `catalogos` endpoints widen that surface again, and they are the one place where the "one `permisos` row per endpoint" rule of spec 06 was broken **on purpose**: no row was seeded for any of them (the "table still has 11 rows" that spec 09 recorded is long out of date — see the spec 14 note below). The stated reason is that every authenticated user needs these reference lists to use the forms they are already allowed to use, so a permission would never be denied to anyone. Do not read the missing rows as an oversight. `GET /catalogos/usuarios` is the consequence to know about: any authenticated user, `Operador` included, gets the `id` and full name of **every** active user, `Admin` accounts included. When the `PermissionsGuard` lands it has to decide whether these three stay open or get rows seeded then.
- Spec 10 is where this stops being only about reads. `PATCH /pesajes/:id/rechazar` is the project's first **write** open to any authenticated user: it deliberately does not call `validateVinculoOperador`, so an `Operador` with no `cliente_operador` row can annul a weigh-in belonging to a client that is not theirs. It also seeds **no** `permisos` row, which is the same exception spec 09 took but with higher stakes — the spec expected the future `PermissionsGuard` to find a destructive operation with no permission code to demand. (That expectation is wrong today: a `RECHAZAR-PESAJE-LOTE` row exists, seeded by hand outside any spec. See the spec 14 note below.) Both were explicit decisions, recorded in `specs/10-rechazo-de-pesajes.md`; neither is an oversight.
- Spec 11 repeats that exception with more at stake. `PATCH /clientes/:id/rechazar` is the second **write** open to any authenticated user, and it also skips `validateVinculoOperador` and seeds **no** `permisos` row (a `RECHAZAR-CLIENTE` row exists anyway, seeded by hand outside any spec — see the spec 14 note below). Where spec 10 annulled one weigh-in row, this makes a whole client vanish from both `GET /clientes` and `GET /clientes/all` and makes `POST /lotes` reject it — an `Operador` with no `cliente_operador` row for that client gets **200, not 403**, and there are two acceptance criteria in `specs/11-rechazo-de-clientes.md` asserting exactly that. So spec 11 expected the future `PermissionsGuard` to find **two** destructive operations with no permission code to demand. The decision was taken with that consequence on the table; it is not an oversight. (The consequence did not materialise: both codes exist in the DB — see the spec 14 note below.) Two more consequences worth knowing before touching this area: the rejection **frees** the client's `rtn` and `codigo_exportacion` for reuse (both validators filter `isActive = 1` since commit `c60e9dc`), so `clientes` can end up with two rows sharing an RTN — one active, one rejected; and because there is no cascade, `GET /lotes/cliente/:clienteId` still returns a rejected client's lotes and `POST /pesajes` still accepts weigh-ins against them, since neither validates `clientes.isActive`.
- Spec 12 makes it three. `PATCH /lotes/:id/rechazar` is the third **write** open to any authenticated user, skips `validateVinculoOperador` and seeds **no** `permisos` row (a `RECHAZAR-LOTE` row exists anyway — see the spec 14 note below). What is different here — and worse than in spec 11 — is that it breaks the convention *inside a file that keeps it*: `LotesRepository` validates the link in **both** of its pre-existing methods, `getLotesByCliente` and `createLote`, so `rechazarLote` is the one method of that class that skips it, and it is the destructive one. Spec 12 expected the future `PermissionsGuard` to find **three** destructive operations with no permission code to demand; all three codes are in fact in the DB. Recorded in `specs/12-rechazo-de-lotes.md` with two acceptance criteria asserting the **200, not 403**; not an oversight.
- Spec 13 makes it four, and it is the first one that is **not destructive**. `PATCH /lotes/:id/aprobar` moves a lote forward to the `CLIENTE_FINAL` stage and closes it; it also skips `validateVinculoOperador` and seeds **no** `permisos` row (an `APROBAR-LOTE` row exists anyway — see the spec 14 note below). So `LotesRepository` now has two of its four methods validating the link (`getLotesByCliente`, `createLote`) and two skipping it (`rechazarLote`, `aprobarLote`). The consequence to hold on to is different in kind from the three rejections: an `Operador` with no `cliente_operador` row can **approve** — sign off on — another client's lote and get **200, not 403**, with `aprobado_por` recording their user id as the supervisor who did it. Recorded in `specs/13-aprobacion-de-lotes.md`; not an oversight. Spec 13 expected the future `PermissionsGuard` to find **four** writes with no permission code to demand — read the next two bullets before believing that.
- Spec 14 changed the *shape* of all this, not the behaviour. `permisos` is no longer "the permissions" — it is now a pure bridge, one row per `(rol_id, permiso_id)`, and the `codigo`/`nombre`/`descripcion` moved to a new `catalogo_permisos`. `GET /permisos/me` reads exactly the same codes through an `INNER JOIN` and its response is byte-identical. **Nothing became enforced**: there is still no `PermissionsGuard`, no `@Permisos()` decorator, `req.user` is still `{ userId, username }` and an `OPERADOR` still gets a 201 from `POST /clientes`. What did change is the cost of fixing this later: seeding, renaming or retiring a permission is now one row in the catalogue instead of one per role.
- **Read this before trusting any permission count or code name written above or below.** Implementing spec 14 required reading the table, and what is in the DB is not what specs 06 and 08 seeded. **Every "(still 11 rows)" and every `modulo.accion` code name in this file is wrong**, and so is the repeated conclusion that the four writes have no permission code. The facts, verified against MySQL: the table holds **14 rows over 9 codes**, none of them one of spec 06's seven; the codes are `APROBAR-LOTE`, `CREAR-CLIENTE-LOTE-NUEVO`, `CREAR-CLIENTE-NUEVO`, `MODULO-CLIENTES`, `MODULO-CONTROL-CALIDAD`, `RECHAZAR-CLIENTE`, `RECHAZAR-LOTE`, `RECHAZAR-PESAJE-LOTE` and `VER-CLIENTE-LOTES`; the roles are named `ADMIN` (id 2) and `OPERADOR` (id 1) in **uppercase**, so any `INSERT ... WHERE r.nombre = 'Admin'` copied from spec 06 matches nothing; and the split is **7 codes each**, with `OPERADOR` holding both client-creation permissions that `ADMIN` lacks, and `ADMIN` holding `RECHAZAR-CLIENTE` and `RECHAZAR-PESAJE-LOTE` that `OPERADOR` lacks. Someone seeded all of this by hand and **no spec records it** — not who, not when, not by what criterion. Two consequences worth holding on to. First: **the four writes of specs 10 to 13 do have permission codes** (`RECHAZAR-PESAJE-LOTE`, `RECHAZAR-CLIENTE`, `RECHAZAR-LOTE`, `APROBAR-LOTE`), so the `PermissionsGuard` will not have to invent them — it will have to decide whether to trust codes no spec designed. Second: the format is `MAYUSCULAS-CON-GUIONES`, which is exactly what spec 06 explicitly rejected, and two of the nine (`MODULO-CLIENTES`, `MODULO-CONTROL-CALIDAD`) are not endpoint permissions at all but screen-access ones, so the guard has two kinds of permission to handle, not one. Spec 14 deliberately did **not** normalise any of this — renaming a code would change what `GET /permisos/me` returns — but it is now a one-`UPDATE`-per-code job. The `descripcion` of each row says which endpoint it means; the transcription is in `specs/14-catalogo-de-permisos.md`. Endpoints with **no** code at all include `POST /pesajes`, `GET /clientes`, `GET /clientes/all`, the three `GET /catalogos/*` and `POST /auth/register`.
- Spec 15 is the first entry in this list that is **not** a widening of the access surface, and it is worth reading as the counter-example to everything above. `GET /pesajes/historial` filters by `pesajes.usuario_id = req.user.userId` and takes no parameter of any kind, so it is the first read endpoint that **cannot** be pointed at someone else's data: there is nowhere to write another user's id. It seeds no `permisos` row — the sixth consecutive spec to skip the rule of spec 06 — but for once the argument is not a risk being accepted: a permission to read your own history would never be denied to anyone. Do **not** file it alongside the routes that skip `validateVinculoOperador`; it skips the check because there is nothing to authorize, not because a spec decided to look away. What it *does* widen is what a caller can see about rows they already own: it applies no `lotes.estado` and no `clientes.isActive` filter, so it is the only endpoint in the project that returns the `nombre_lote` of a closed lote and the `nombre` of a rejected client. In the current DB that is not a corner case — 24 of one user's 28 active weigh-ins hang off rejected clients.

**Module layout convention:** each feature module is `*.module.ts` → `*.controller.ts` → `*.service.ts` → `repository/*.repository.ts` → `dto/*.dto.ts` (Zod schemas), with `imports: [DatabaseModule]` in the module and the module registered in `src/app.module.ts`.

- Controllers stay thin and always respond with the shape `{ ok, msg, <payload> }`. The payload key is named after the resource (`clientes`, `lotes`, `permisos`) everywhere **except** the three spec 09 `catalogos` endpoints, which use `data` so all three share one response shape. That inconsistency is a recorded decision, not drift — if it is ever unified, unify all ten `GET`s in one spec — the seven with a named key and the three with `data` — rather than "fixing" one side.
- Services are pure pass-throughs to the repository.
- **The repository is where business logic lives**, not just data access: `AuthRepository` hashes passwords with `bcrypt` and signs the JWT via `JwtService`; `ClientesRepository`/`LotesRepository`/`PesajesRepository` hold all domain validation and derived-value computation (e.g. `peso_neto`, `fuera_de_rango`). Don't assume repositories are pure data-access when extending this pattern. `CatalogosRepository` (spec 09) is the one exception in the other direction: three plain `SELECT`s, no validation, no transaction, no input.
- **Write path convention:** every create opens `this.db.transaction().execute(async (trx) => ...)`, runs a series of `private async validateX(..., db: Kysely<Database>)` helpers **inside** the transaction (they take the `trx` so validation and insert share a connection), then inserts and returns `Number(result.insertId)`. Validators throw `BadRequestException` for missing/inactive rows and duplicates, `ForbiddenException` for authorization. Copy this shape for new modules. The project's only four **`UPDATE`**s are spec 10's `rechazarPesaje`, spec 11's `rechazarCliente`, spec 12's `rechazarLote` and spec 13's `aprobarLote`; all four keep the same shape (transaction, validators taking the `trx`), return `true` instead of an id, and write their timestamps with `sql\`NOW()\`` rather than a Node `new Date()` so they share a clock with `created_at` — but see the access-control note above before copying any of them. `rechazarLote` is the widest at six columns; `aprobarLote` writes five and is the only one that runs three validators plus a catalog resolve. Both resolve a foreign row (`etapas` by `codigo`) inside the transaction before writing, the way `resolveEstadoCalidad` does in `PesajesRepository`. Resolving a catalog row by its `codigo` rather than a hardcoded id is the convention to copy — `createLote`'s `etapa_id: 1` literal is the counter-example, left in place on purpose. Note also that `aprobarLote` takes `(loteId, userId)` with **no DTO**: `PATCH /lotes/:id/aprobar` is the project's only write endpoint with no request body and no Zod schema, because the spec gave approval no free-text field.
- **Access control convention:** most operations touching a client's data call a `validateVinculoOperador(clienteId, usuarioId, db)`-style check against `cliente_operador` first. For `pesajes` the `cliente_id` is resolved from the lote first. **This is no longer a rule the codebase actually holds to** — **eight** endpoints deliberately skip the check: spec 08's `GET /clientes/all`, spec 09's three `catalogos` reads, the three `rechazar` writes of specs 10, 11 and 12, and spec 13's `PATCH /lotes/:id/aprobar`. (That list said "seven" from spec 13 until spec 15 counted it; the eight names have not changed.) A **ninth**, `GET /lotes/cliente/:clienteId/all`, never had it and no spec ever decided that — it just sits next to a route that does validate. The four writes matter most, and the pattern is almost the same in all of them: **the method that guards is the one that creates, not the one that ends the row's life.** `PesajesRepository` has `createPesaje` validating the link and `rechazarPesaje` a few lines below it not validating it; `LotesRepository` validates it in `getLotesByCliente` and `createLote` but in neither `rechazarLote` nor `aprobarLote`; `ClientesRepository` does not validate it on **either** of its writes, so nothing in the `clientes` module checks `cliente_operador` on the write path at all. Do not copy any `rechazar*` or `aprobarLote` method as the template for a new write. Today the `GET /clientes` filter is cosmetic for anyone who knows the other routes exist, and so is the one on `GET /lotes/cliente/:clienteId`. Spec 15's `GET /pesajes/historial` does not validate the link either, but **do not count it as a ninth**: it filters by the caller's own `usuario_id` and accepts no parameter, so there is no other user's data it could reach. It is the one place in the project where "no `validateVinculoOperador`" is a fact about the query shape rather than a decision to skip a check.
- Uniqueness (`clientes.rtn`, `clientes.codigo_exportacion`, `lotes.nombre_lote` per client) is enforced **in application code only** — there are no matching MySQL constraints, by explicit decision. This leaves a known race window between the validating `SELECT` and the `INSERT`. All three validators also **exclude rejected rows**, so a rejection frees the value for reuse and the table can end up holding duplicates: `clientes` two rows with one `rtn`, `lotes` two rows with one `nombre_lote` for a client. Note the two do it differently, and the difference is load-bearing: the `clientes` validators filter `isActive = 1`, but `validateNombreLoteDisponible` filters **`motivo_rechazo IS NULL`, not `estado`** — because spec 12 made a rejected lote `estado = 'cerrado'`, filtering on the state would also free the name of lotes closed for any other reason. `motivo_rechazo` is the only column written exclusively by the rejection. Since spec 13 that is no longer hypothetical: an **approved** lote is also `estado = 'cerrado'` but has `motivo_rechazo IS NULL`, so its `nombre_lote` correctly stays reserved while a rejected one's is freed. Do not "simplify" that filter to `estado <> 'cerrado'`.

Import path convention: absolute imports from `src/...` are used throughout (e.g. `src/decorators/public.decorator`) rather than relative `../../` paths, even for same-module files in some cases — follow existing files' style per-file rather than assuming one rule.

| `auth` | `POST /auth/login`, `POST /auth/register` (both `@Public()`) |
| `clientes` | `POST /clientes` (optional `usuario_ids` links operators), `GET /clientes` (only clients linked to the caller via `cliente_operador`), `GET /clientes/all` (spec 08; **every** active client, no `cliente_operador` filter, same six fields as `GET /clientes`; declared by a `clientes.listar_todos` row that spec 08 seeded for `Admin` only and that is **no longer in the DB** — see the spec 14 note in the auth section; either way it was never enforced, so any authenticated user, `OPERADOR` included, gets 200 with the full list), `PATCH /clientes/:id/rechazar` (spec 11; **logical deactivation** of the client, not an approval flow — there is no `clientes.estado` column and `POST /clientes` still creates immediately-usable clients. Responds `{ ok, msg }` with **no resource payload** — the second endpoint that returns nothing of what it touched, matching the other `rechazar`. 400 if the client does not exist or is already rejected (`isActive = 0`; a row with `isActive = NULL` is *not* considered rejected and can be rejected). Irreversible: nothing can undo it and no endpoint lists rejected clients, so the client becomes unreachable by API. **No cascade** — the client's lotes stay open, their pesajes stay active and its `cliente_operador` rows are left intact. **Does not check `cliente_operador` and has no `permisos` row** — see the auth notes) |
| `lotes` | `POST /lotes` (inserts `estado: 'abierto'` and a hardcoded `etapa_id: 1`), `GET /lotes/cliente/:clienteId` (product, unit and *etapa* resolved to names by join; filtered `estado = 'abierto'`, ordered `created_at` DESC; never exposes `resumen_ia`; validates `cliente_operador`), `GET /lotes/cliente/:clienteId/all` (spec 12 documented it after the fact; the **same query and the same fields** as the route above — the only difference is that it does **not** validate `cliente_operador`, so any authenticated user gets any client's lotes. Despite the name it is *not* "all lotes": it filters `estado = 'abierto'` too, so it hides rejected ones exactly like the other), `PATCH /lotes/:id/rechazar` (spec 12; **logical annulment** of the lote. Writes six columns: `estado = 'cerrado'`, `etapa_id` = the `etapas` row with `codigo = 'RECHAZADO'` (resolved by `codigo`, never by a hardcoded id), `cerrado_en = NOW()`, plus the audit trio `motivo_rechazo`/`rechazado_por`/`rechazado_en`. Body is one required `motivo`, 5–255 chars. Responds `{ ok, msg }` with **no resource payload** — the third endpoint that returns nothing of what it touched, matching the other two `rechazar`. 400 if the lote does not exist, is not open (`estado != 'abierto'` or `cerrado_en != NULL`, which is also how "already rejected" is caught — there is no dedicated message for it), or if the `RECHAZADO` row is missing from `etapas`. Irreversible: nothing can undo it and no endpoint lists rejected lotes. **No cascade** — the lote's pesajes stay active, so `GET /pesajes/byLote/:loteId` still returns them while `POST /pesajes` and `PATCH /pesajes/:id/rechazar` both start returning 400, which makes those pesajes impossible to annul. **Frees the `nombre_lote`** for reuse in that client. **Does not check `cliente_operador` and has no `permisos` row** — see the auth notes), `PATCH /lotes/:id/aprobar` (spec 13; the supervisor signs the lote off and it moves to the next stage of the diagram. Writes five columns: `estado = 'cerrado'`, `etapa_id` = the `etapas` row with `codigo = 'CLIENTE_FINAL'` (resolved by `codigo`, never by the id 2), `cerrado_en = NOW()`, plus `aprobado_por`/`aprobado_en`. **No request body and no DTO** — the only write endpoint in the project without either, because approval carries no free-text field. Responds `{ ok, msg }`, matching the three `rechazar`. 400 if the lote does not exist, is not open (`estado != 'abierto'` or `cerrado_en != NULL`, which is also how "already approved" and "already rejected" are caught — there is no dedicated message for either), if its current `etapa_id` is not the `EN_PROCESO` row, if it has **no pesaje with `isActive = 1`**, or if the `EN_PROCESO`/`CLIENTE_FINAL` row is missing from `etapas`. Irreversible: nothing can undo it and no endpoint lists approved lotes. **No cascade** — the lote's pesajes stay active. Does **not** free the `nombre_lote` (that needs `motivo_rechazo`, which approval never writes). Note what closing the lote costs: `POST /pesajes` and `PATCH /pesajes/:id/rechazar` both start returning 400, so **no weighing is possible at the `CLIENTE_FINAL` stage** even though `diagram.jpeg` puts the supervisor-PIN flow there — an explicit decision, recorded in `specs/13-aprobacion-de-lotes.md`, not an oversight. **Does not check `cliente_operador` and has no `permisos` row** — see the auth notes) |
| `pesajes` | `POST /pesajes` (one weigh-in per request; backend computes `peso_neto = peso_bruto - tara`, `fuera_de_rango` and `estado_calidad_id` — the body accepts none of the three), `GET /pesajes/byLote/:loteId` (weigh-ins of one lote, quality state and user resolved to names by join, filtered `isActive = 1`, ordered `created_at` DESC; exists since spec 03 but was undocumented here until spec 10), `GET /pesajes/historial` (spec 15; the caller's own weigh-in history. **The filter is the token** — `pesajes.usuario_id = req.user.userId` — so it takes no path param, no query param and no body, and there is no way to ask for anyone else's. Thirteen fields: the twelve of `byLote` **minus** `usuarios.complete_name as usuario` (redundant — every row is yours, and the join to `usuarios` is gone with it), **plus** `lotes.nombre_lote as lote` and `clientes.nombre as cliente`. Filters `isActive = 1`, ordered `created_at` DESC, `{ ok, msg, pesajes }`. What it deliberately does **not** filter is the point of the endpoint: no `lotes.estado`, no `clientes.isActive` and no `cliente_operador`, so it is **the only endpoint that returns the `nombre_lote` of a closed lote and the `nombre` of a rejected client** — data every other read hides — and an operator unlinked from a client keeps seeing what they weighed for it. Three `LEFT JOIN`s, so a pesaje with a null `lote_id` would come back with `lote: null`/`cliente: null` rather than vanish. No pagination, no limit, no date range. Never 404 and never 400: it does not query `usuarios`, so a token whose user no longer exists gets **200 with `[]`**, unlike `GET /permisos/me`. Rejected weigh-ins stay invisible here too. **Has no `permisos` row** — but unlike the routes listed in the auth notes, "does not check `cliente_operador`" is not a gap here: there is nothing to authorize), `PATCH /pesajes/:id/rechazar` (spec 10; **logical annulment**, not the diagram's `RECHAZADO` quality state — sets `isActive = 0` plus `motivo_rechazo`, `rechazado_por` and `rechazado_en`, leaving weights and `estado_calidad_id` untouched. Body is one required `motivo`, 5–255 chars. Responds `{ ok, msg }` with **no resource payload** — the only endpoint that returns nothing of what it touched. 400 if the pesaje does not exist, is already rejected, has a null `lote_id`, or its lote is not open. Irreversible: nothing can undo it and no endpoint lists rejected weigh-ins. **Does not check `cliente_operador` and has no `permisos` row** — see the auth notes) |
| `permisos` | `GET /permisos/me` (spec 07; resolves `rol_id` from the JWT's `userId`, returns a flat `string[]` of the role's permission codes, unordered; 404 if the user no longer exists, `[]` if the role has none — **informational only, nothing is enforced**. Since spec 14 the second query is an `INNER JOIN` from `permisos` to `catalogo_permisos` on `permiso_id`, selecting `catalogo_permisos.codigo` and requiring **both** `isActive` columns to be `1` — the code lives in the catalogue now, not in `permisos`. The response contract did not change: same flat `string[]`, same `{ ok, msg, permisos }`, same codes) |
| `catalogos` | `GET /catalogos/productos`, `GET /catalogos/usuarios`, `GET /catalogos/unidades-medida` (spec 09; read-only selector lists. Each returns `{ ok, msg, data }` where every element is exactly `{ id, nombre }` — **`data` is the payload key, not a named one**, the only three endpoints in the project that break the `{ ok, msg, <named payload> }` convention, by explicit decision. `productos` and `usuarios` filter `isActive = 1`; `unidades_medida` has no such column so it is unfiltered. `usuarios` aliases `complete_name as nombre` and returns **every** active user with no role filter and no `cliente_operador` filter. Ordered by `nombre` / `complete_name` ASC. No permission row is seeded for any of them — deliberately, see the auth notes) |

Beyond the `GET`s above and the four `PATCH`es of specs 10, 11, 12 and 13, there is no `GET /clientes/:id`, no `GET /lotes/:id`, no `PUT` or `DELETE` anywhere, and no CRUD on the three catalog tables. Those four routes — three `rechazar` plus one `aprobar` — are the project's only non-`GET`/`POST` routes, its only four `UPDATE`s, and — with `GET /pesajes/byLote/:loteId` and the two `GET /lotes/cliente/:clienteId*` taking other param names — its only four `:id` path params. Deletion is always logical (`isActive = 0` on `pesajes`/`clientes`, `estado = 'cerrado'` on `lotes`); nothing issues a `DELETE FROM`. If `GET /clientes/:id` is ever added, declare it **after** `@Get('all')` in `ClientesController` or it will swallow `/clientes/all`; the same trap waits in `LotesController`, where a `GET /lotes/:id` declared before the two `cliente/...` routes would swallow both. Specs 11, 12 and 13 already put a `:id` in one of those controllers, on `PATCH` — two of them in `LotesController` — which makes the mistake easier to make. Since spec 15 `PesajesController` is the third such place: a `GET /pesajes/:id` declared before `@Get('historial')` would swallow `/pesajes/historial` and answer it with a `ParseIntPipe` 400. `historial` is already declared first in that file precisely so a `:id` appended at the end is harmless.

Every route Nest maps is now covered by a spec: `GET /pesajes/byLote/:loteId` was documented after the fact by spec 10, and `GET /lotes/cliente/:clienteId/all` by spec 12. Trust the route log over this table if the two ever disagree.

**Read this before touching anything that reads `lotes.estado`.** Since spec 13, `estado = 'cerrado'` means **two different things** and the column alone cannot tell them apart — nor can `cerrado_en`, which both operations write with the same `NOW()`:

| Signal | Rejected lote | Approved lote |
| --- | --- | --- |
| `estado` | `'cerrado'` | `'cerrado'` — **useless as a discriminator** |
| `cerrado_en` | written | written — **also useless** |
| `motivo_rechazo` | `NOT NULL` | `NULL` — **the canonical signal of a rejection** |
| `aprobado_por` / `aprobado_en` | `NULL` | `NOT NULL` — **the canonical signal of an approval** |
| `etapa_id` | `RECHAZADO` row | `CLIENTE_FINAL` row — usable, but needs an `etapas` lookup and the column is nullable |

The two audit columns are mutually exclusive by construction, because both endpoints require the lote to be open before writing. So: a rejected lote is `motivo_rechazo IS NOT NULL`, an approved lote is `aprobado_por IS NOT NULL`, and `'cerrado'` on its own says only "no longer open". And note what still does **not** exist: there is no closing of a lote as a *computation* — no aggregates, no `resumen_ia`, no `FINALIZADO`. `etapas` now has three of its four rows written by code — `EN_PROCESO` by `createLote`'s hardcoded literal, `RECHAZADO` by `rechazarLote`, `CLIENTE_FINAL` by `aprobarLote` — and **`FINALIZADO` is never written by anything.**

## Domain

This is a quality-control system for agricultural export batches. Core tables (see `src/database/types/types.ts`): `clientes` (clients/companies, with an `isActive` logical-deletion flag and — since spec 11 — the same rejection audit trio as `pesajes`: `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /clientes/:id/rechazar`), `cliente_operador` (many-to-many between clients and operator users), `lotes` (batches tied to a client + product, with `peso_minimo`/`peso_ideal`/`peso_maximo` tolerance range, an `etapa_id` pointing at `etapas`, an `estado`/`cerrado_en` lifecycle and — since spec 12 — the same rejection audit trio as `pesajes` and `clientes`: `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /lotes/:id/rechazar` — plus, since spec 13, the approval pair `aprobado_por`/`aprobado_en`, both nullable, written only by `PATCH /lotes/:id/aprobar`), `etapas` (the stage of the flow a lote is in — `EN_PROCESO` = id 1, `CLIENTE_FINAL` = id 2, `RECHAZADO` = id 3, `FINALIZADO` = id 4 in the current DB, each with a `codigo` like `EN_PROCESO` and a `nombre` like `EN PROCESO`; seeded by hand, no endpoint reads or writes the table itself and **no spec designed it** — spec 12 consumed the `RECHAZADO` row and spec 13 the `EN_PROCESO` and `CLIENTE_FINAL` ones, both resolving by `codigo`; the rest, including `createLote`'s hardcoded `etapa_id: 1`, is left for a future spec. Never hardcode these ids: they differ between environments, which is why both `PATCH`es resolve by `codigo`), `pesajes` (individual weigh-ins against a lote, with `peso_bruto`/`tara`/`peso_neto`, `fuera_de_rango`, and — since spec 10 — an `isActive` logical-deletion flag plus the rejection audit trio `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /pesajes/:id/rechazar`), `estados_calidad` (quality states applied to a pesaje), `productos`, `unidad_medida`, and `roles`/`usuarios` for auth, plus the permission pair, refactored by spec 14 into a catalogue and a bridge: `catalogo_permisos` (the permission definitions — one row per `codigo`, with `nombre`, `descripcion`, `isActive` and a **globally** `UNIQUE` `codigo`) and `permisos` (the assignment — one row per `(rol_id, permiso_id)`, with **no text of its own**, a `UNIQUE (rol_id, permiso_id)` and FKs to both `roles(id)` and `catalogo_permisos(id)`). The `codigo` no longer lives in `permisos`: `SELECT codigo FROM permisos` is now an error, and reading it means joining. Renaming a permission is one `UPDATE` on the catalogue instead of one per role — that was the whole point of spec 14. Note the two `isActive`, which are **not** redundant: `catalogo_permisos.isActive = 0` retires a permission from the entire system in one row, `permisos.isActive = 0` retires it from one role only, and `GET /permisos/me` requires both to be `1`. Still **not enforced anywhere**; see the auth/guard notes above.

`diagram.jpeg` in the repo root is the intended end-to-end weighing flow and is the best reference for where the product is going. The backend currently implements only its happy path (capture weight → in range → save). **Not yet built, and needed by the diagram:** the rest of the *Etapa* flow — spec 13 built the first forward transition, `EN_PROCESO` → `CLIENTE_FINAL` via `PATCH /lotes/:id/aprobar`, but `FINALIZADO` is still never written and there is no `CLIENTE_FINAL` → `FINALIZADO` endpoint. Worse for the diagram: approving **closes** the lote (`estado = 'cerrado'`), so `POST /pesajes` returns 400 from then on and **weighing at the final-client stage is impossible** — the diagram's supervisor-PIN flow lives exactly there. That was an explicit decision in `specs/13-aprobacion-de-lotes.md`, taken with the consequence on the table; unblocking it means deciding whether approval stops closing the lote or `validateLoteAbierto` changes. Also missing: automatic derivation of the quality state (`APROBADO` / `APROBADO CON EXCEPCIÓN` / `RECHAZADO` — today `estado_calidad_id` comes from the request body and is only checked for existence), alert severity (today only a `fuera_de_rango` boolean, no yellow/red distinction), and supervisor PIN authorization for out-of-range weigh-ins at the final-client stage.

Also deferred by the existing specs, and worth knowing before proposing work: **closing a lote as a computed result** — read this carefully, because specs 12 and 13 both changed the situation without implementing it. `rechazarLote` and `aprobarLote` each write `estado = 'cerrado'` and `cerrado_en = NOW()`, so those columns are well past untouched, but there is still **no** endpoint that closes a lote on a computed result, no aggregates and no `resumen_ia`. The consequence to hold on to: **`estado = 'cerrado'` says only "no longer open"** — it does not say whether the lote was rejected or approved, and it does not mean closing exists. Use `motivo_rechazo IS NOT NULL` for a rejection and `aprobado_por IS NOT NULL` for an approval; see the discriminator table above the Domain section. Whoever implements real closing inherits this: `'cerrado'` is already taken by two different operations and all three will need telling apart. Also deferred: per-lote aggregates (total weight, counts by quality state), `resumen_ia` generation, batch/offline weigh-in sync and device idempotency by `(dispositivo_identificador, secuencia_dispositivo)`, and endpoints to manage `cliente_operador` links after a client is created.

MySQL decimal columns (`peso_*`) come back from the driver as `string | number`, and `pesajes.id` is a `BIGINT` typed as `Generated<string | number>` — coerce with `Number()` before comparing or returning.

## Caveats

- Any DDL is applied **by hand in MySQL**; there is no migration tooling and no `.sql` files in the repo. When a change needs schema work, document the DDL in the spec and update `src/database/types/types.ts` to match. (Specs 02 and 03 state "no DDL" as a decision — note that `pesajes.fuera_de_rango` was in fact added during spec 03, so that spec's acceptance criterion is inaccurate.) Specs 10 through 13 are the only specs so far that declare their DDL up front, and 10, 11 and 12 declare the same shape on three tables: three nullable columns (`motivo_rechazo VARCHAR(255)`, `rechazado_por INT`, `rechazado_en DATETIME`) on `pesajes`, then `clientes`, then `lotes`, each with a real FK from `rechazado_por` to `usuarios(id)`. The names are identical on purpose — it is the same operation on another table and the audit trail should read the same in all three. Spec 13 adds the mirror pair on `lotes` alone: `aprobado_por INT NULL` with its own FK to `usuarios(id)`, and `aprobado_en DATETIME NULL`. There is no third text column, because approval carries no motivo. Those four FKs are the second through fifth exceptions to the application-code-only rule, after `permisos` → `roles`, justified as audit columns that would be worthless pointing at a missing user. Spec 14 adds the sixth, `permisos.permiso_id` → `catalogo_permisos(id)`, and is the first spec whose DDL is **destructive**: it drops three columns and an index off a table with data. The order it uses is the part to copy — create the new unique index, drop the old one, drop the columns, add the FK, and do all of it only *after* the code has stopped reading those columns. Neither spec 12 nor spec 13 needed DDL beyond their columns: `lotes.estado` is a plain `VARCHAR(20)` (with `DEFAULT 'abierto'`), so writing `'cerrado'` never required touching it.
- `permisos` is seeded and maintained **by hand in SQL** — there is no CRUD endpoint (`GET /permisos/me` only reads) and nothing validates it at startup. Since spec 14 that means **two** inserts: one row in `catalogo_permisos` for the code itself, then one row in `permisos` per role that should have it (`INSERT ... SELECT r.id, c.id FROM roles r JOIN catalogo_permisos c ON c.codigo = '<CODIGO>' WHERE r.nombre = '<ROL>'`, resolving both ids by their natural key because ids differ between environments). Note the role names are `ADMIN` and `OPERADOR` in **uppercase** — spec 06's seed SQL says `'Admin'` and would match nothing. Nothing will warn you if you forget. There are seven deliberate exceptions to that rule, so the rule has now gone unmet in six consecutive specs. Spec 07: `GET /permisos/me` has no permission row of its own, because requiring a permission to read your own permissions is circular. Spec 09: none of the three `catalogos` endpoints has one either — not circular, just a judgement call that reference lists everyone needs should not gate behind a permission nobody would be denied. Specs 10, 11 and 12: none of the three `rechazar` endpoints has one, which is the same judgement call applied to three destructive writes. Spec 13: `PATCH /lotes/:id/aprobar` has none either. Spec 15: `GET /pesajes/historial` has none, and it is the one exception whose argument is not a risk being accepted — the endpoint only ever returns the caller's own rows, so the permission could never be denied to anyone. Spec 08 followed the rule and seeded one row, `clientes.listar_todos` for `Admin`. **None of those counts describes the current DB**, and neither does the "11 rows" that specs 08 to 13 all repeat: the table holds 14 rows over 9 codes, none of them spec 06's, and the four writes above *do* have codes — all seeded by hand with no spec recording it. Read the spec 14 bullet in the auth notes before acting on any number in this paragraph. Seeded or not, every row is still unenforced. Note also that the permission tables are the one place where uniqueness is enforced by real MySQL constraints, a deliberate exception to the application-code-only rule above, precisely because no application code writes to them. Since spec 14 there are four: `UNIQUE (codigo)` on `catalogo_permisos` (global, so a code exists once in the whole system), `UNIQUE (rol_id, permiso_id)` on `permisos`, the FK to `roles(id)`, and the new FK from `permisos.permiso_id` to `catalogo_permisos(id)` — the **sixth** exception to the application-code-only rule, after `permisos` → `roles` and the four audit FKs of specs 10 to 13. Same justification as the first: nothing in the app writes these tables, so without the FK a mistyped `permiso_id` would leave a row the `INNER JOIN` silently discards.
