# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run start:dev      # run with watch mode (default for local dev)
npm run start:debug    # watch mode + --inspect
npm run build          # nest build -> dist/
npm run start:prod     # node dist/main (run build first)

npm run lint           # eslint --fix over src/apps/libs/test
npm run format         # prettier --write over src and test

npm run test           # jest unit tests (*.spec.ts, rootDir: src)
npm run test:watch
npm run test:cov
npm run test:e2e       # jest -c ./test/jest-e2e.json
```

Run a single unit test file: `npx jest path/to/file.spec.ts`. There are currently no `*.spec.ts` files or `test/` e2e directory in the repo — testing infra is configured (jest, ts-jest, supertest) but unused so far.

Server listens on `process.env.PORT` (default 4000). No global route prefix is set (the `app.setGlobalPrefix('api/v1')` line in `src/main.ts` is commented out).

Required env vars (see `.env`, not committed): `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `JWT_SECRET`, `PORT`.

## Spec-driven workflow

This repo is developed spec-first via two local skills in `.agents/skills/` (mirrored in `.claude/skills/`):

- `/spec` — designs a spec interactively and saves it to `specs/NN-nombre.md` (template at `.agents/skills/spec/template.md`). No code is written in this phase.
- `/spec-impl <NN-spec-name>` — implements an already-approved spec, creating a git branch named after it.

`specs/` holds the source of truth for what was decided and, just as importantly, what was **deliberately deferred** (each spec has `Out of scope`, `Decisions`, `Risks` and `What is not in this spec` sections). Before adding a feature, check whether an existing spec already ruled it out and why — new work goes in a new spec rather than silently expanding an old one. Specs are written in Spanish; the codebase and this file are in English.

Existing specs (all marked `Implemented`): `01-vinculacion-cliente-operador.md`, `02-modulo-lotes.md`, `03-guardado-de-pesajes.md`.

## Architecture

NestJS API (Express platform) backed by MySQL via Kysely (no ORM, no migrations tooling checked into the repo — the DB schema is assumed to pre-exist and is only mirrored in TypeScript types).

**Request-scoped DB connection pattern** — this is the key non-obvious mechanism:
- `DatabaseMiddleware` (`src/database/middlewares/database.middleware.ts`) runs on every route (`forRoutes('*')`, wired in `DatabaseModule`), opens a new `Kysely` instance with a 1-connection `mysql2` pool per request, and stashes it on `req['db']`. The pool is destroyed when the response finishes (`res.on('finish', ...)`).
- `DatabaseService` (`src/database/database.service.ts`) is `Scope.REQUEST`-scoped and just pulls `request['db']` in its constructor via `@Inject(REQUEST)`.
- Any provider that injects `DatabaseService` becomes request-scoped too (Nest scope propagation), and repositories access the query builder through `this.dbService.client`.
- `Database` and the `*Table` interfaces in `src/database/types/types.ts` are the hand-written Kysely schema — when adding a table/column in MySQL, update this file by hand (no codegen). Note the `Database` key for units is `unidades_medida` (plural) even though the interface is `UnidadMedidaTable`; use the plural form in queries.

**Auth/guard flow:**
- `JwtAuthGuard` (`src/guards/jwt-auth.guard.ts`) is registered globally both via `APP_GUARD` in `AppModule` and again manually in `main.ts` (`app.useGlobalGuards(new JwtAuthGuard(reflector))`), so every route requires a valid JWT by default.
- Use `@Public()` (`src/decorators/public.decorator.ts`) to opt a specific route out — only `AuthController.login` and `AuthController.register` are marked `@Public()`.
- `JwtStrategy` (`src/strategy/jwt.stategy.ts`) validates the bearer token and returns `{ userId, username }`, which becomes `req.user`. Controllers read it as `const { userId } = req.user as { userId: number }`.
- Global pipes: `ZodValidationPipe` from `nestjs-zod` is registered both as `APP_PIPE` in `AppModule` and again manually in `main.ts` — DTOs are Zod schemas wrapped with `createZodDto()` (see `src/modules/*/dto/*.dto.ts`), not `class-validator`.
- Roles exist in the DB (`roles`, `usuarios.rol_id`) but **no endpoint discriminates by role yet** — every authenticated user has the same permissions.
- The `permisos` table (spec 06) declares what each role is *supposed* to be able to do. Exactly one thing reads it — `GET /permisos/me` (spec 07), which hands the caller its own role's codes so a client can hide buttons — and **nothing enforces it**: there is no `PermissionsGuard` and no `@Permisos()` decorator, `req.user` is still `{ userId, username }`, the JWT payload is unchanged (`sub`, `user_id`, `username`) and `POST /auth/login` does not return permissions. An `OPERADOR` still gets a 201 from `POST /clientes` even though the table says they lack `clientes.crear`. Enforcing it is a future spec.
- Spec 08 raised the stakes of that gap. `GET /clientes/all` is declared by `clientes.listar_todos`, seeded for `Admin` only, but nothing reads it on the request path — so an `Operador` calling that route gets 200 with **every** client. It is the first endpoint that opens data previously closed: until the guard lands, the `cliente_operador` filter on `GET /clientes` is bypassable by calling the route next to it.
- Spec 09's three `catalogos` endpoints widen that surface again, and they are the one place where the "one `permisos` row per endpoint" rule of spec 06 was broken **on purpose**: no row was seeded for any of them, so the table still has 11 rows. The stated reason is that every authenticated user needs these reference lists to use the forms they are already allowed to use, so a permission would never be denied to anyone. Do not read the missing rows as an oversight. `GET /catalogos/usuarios` is the consequence to know about: any authenticated user, `Operador` included, gets the `id` and full name of **every** active user, `Admin` accounts included. When the `PermissionsGuard` lands it has to decide whether these three stay open or get rows seeded then.
- Spec 10 is where this stops being only about reads. `PATCH /pesajes/:id/rechazar` is the project's first **write** open to any authenticated user: it deliberately does not call `validateVinculoOperador`, so an `Operador` with no `cliente_operador` row can annul a weigh-in belonging to a client that is not theirs. It also seeds **no** `permisos` row (the table is still at 11), which is the same exception spec 09 took but with higher stakes — the future `PermissionsGuard` will find a destructive operation with no permission code to demand, and will have to invent one. Both were explicit decisions, recorded in `specs/10-rechazo-de-pesajes.md`; neither is an oversight.
- Spec 11 repeats that exception with more at stake. `PATCH /clientes/:id/rechazar` is the second **write** open to any authenticated user, and it also skips `validateVinculoOperador` and seeds **no** `permisos` row (still 11). Where spec 10 annulled one weigh-in row, this makes a whole client vanish from both `GET /clientes` and `GET /clientes/all` and makes `POST /lotes` reject it — an `Operador` with no `cliente_operador` row for that client gets **200, not 403**, and there are two acceptance criteria in `specs/11-rechazo-de-clientes.md` asserting exactly that. So the future `PermissionsGuard` now finds **two** destructive operations with no permission code to demand, and will have to invent both. The decision was taken with that consequence on the table; it is not an oversight. Two more consequences worth knowing before touching this area: the rejection **frees** the client's `rtn` and `codigo_exportacion` for reuse (both validators filter `isActive = 1` since commit `c60e9dc`), so `clientes` can end up with two rows sharing an RTN — one active, one rejected; and because there is no cascade, `GET /lotes/cliente/:clienteId` still returns a rejected client's lotes and `POST /pesajes` still accepts weigh-ins against them, since neither validates `clientes.isActive`.
- Spec 12 makes it three. `PATCH /lotes/:id/rechazar` is the third **write** open to any authenticated user, skips `validateVinculoOperador` and seeds **no** `permisos` row (still 11). What is different here — and worse than in spec 11 — is that it breaks the convention *inside a file that keeps it*: `LotesRepository` validates the link in **both** of its pre-existing methods, `getLotesByCliente` and `createLote`, so `rechazarLote` is the one method of that class that skips it, and it is the destructive one. The future `PermissionsGuard` now finds **three** destructive operations with no permission code to demand. Recorded in `specs/12-rechazo-de-lotes.md` with two acceptance criteria asserting the **200, not 403**; not an oversight.

**Module layout convention:** each feature module is `*.module.ts` → `*.controller.ts` → `*.service.ts` → `repository/*.repository.ts` → `dto/*.dto.ts` (Zod schemas), with `imports: [DatabaseModule]` in the module and the module registered in `src/app.module.ts`.

- Controllers stay thin and always respond with the shape `{ ok, msg, <payload> }`. The payload key is named after the resource (`clientes`, `lotes`, `permisos`) everywhere **except** the three spec 09 `catalogos` endpoints, which use `data` so all three share one response shape. That inconsistency is a recorded decision, not drift — if it is ever unified, unify all seven `GET`s in one spec rather than "fixing" one side.
- Services are pure pass-throughs to the repository.
- **The repository is where business logic lives**, not just data access: `AuthRepository` hashes passwords with `bcrypt` and signs the JWT via `JwtService`; `ClientesRepository`/`LotesRepository`/`PesajesRepository` hold all domain validation and derived-value computation (e.g. `peso_neto`, `fuera_de_rango`). Don't assume repositories are pure data-access when extending this pattern. `CatalogosRepository` (spec 09) is the one exception in the other direction: three plain `SELECT`s, no validation, no transaction, no input.
- **Write path convention:** every create opens `this.db.transaction().execute(async (trx) => ...)`, runs a series of `private async validateX(..., db: Kysely<Database>)` helpers **inside** the transaction (they take the `trx` so validation and insert share a connection), then inserts and returns `Number(result.insertId)`. Validators throw `BadRequestException` for missing/inactive rows and duplicates, `ForbiddenException` for authorization. Copy this shape for new modules. The project's only three **`UPDATE`**s are spec 10's `rechazarPesaje`, spec 11's `rechazarCliente` and spec 12's `rechazarLote`; all three keep the same shape (transaction, validators taking the `trx`), return `true` instead of an id, and write `rechazado_en` with `sql\`NOW()\`` rather than a Node `new Date()` so the timestamp shares its clock with `created_at` — but see the access-control note above before copying any of them. `rechazarLote` is the widest of the three: six columns instead of four, and it resolves a foreign row (`etapas` by `codigo`) inside the transaction before writing, the way `resolveEstadoCalidad` does in `PesajesRepository`. Resolving a catalog row by its `codigo` rather than a hardcoded id is the convention to copy — `createLote`'s `etapa_id: 1` literal is the counter-example, left in place on purpose.
- **Access control convention:** most operations touching a client's data call a `validateVinculoOperador(clienteId, usuarioId, db)`-style check against `cliente_operador` first. For `pesajes` the `cliente_id` is resolved from the lote first. **This is no longer a rule the codebase actually holds to** — six endpoints deliberately skip the check: spec 08's `GET /clientes/all`, spec 09's three `catalogos` reads, and the three `rechazar` writes of specs 10, 11 and 12. A seventh, `GET /lotes/cliente/:clienteId/all`, never had it and no spec ever decided that — it just sits next to a route that does validate. The three writes matter most, and the pattern in all three is the same: **the method that guards is the one that creates, not the one that destroys.** `PesajesRepository` has `createPesaje` validating the link and `rechazarPesaje` a few lines below it not validating it; `LotesRepository` validates it in both `getLotesByCliente` and `createLote` but not in `rechazarLote`; `ClientesRepository` does not validate it on **either** of its writes, so nothing in the `clientes` module checks `cliente_operador` on the write path at all. Do not copy any `rechazar*` method as the template for a new write. Today the `GET /clientes` filter is cosmetic for anyone who knows the other routes exist, and so is the one on `GET /lotes/cliente/:clienteId`.
- Uniqueness (`clientes.rtn`, `clientes.codigo_exportacion`, `lotes.nombre_lote` per client) is enforced **in application code only** — there are no matching MySQL constraints, by explicit decision. This leaves a known race window between the validating `SELECT` and the `INSERT`. All three validators also **exclude rejected rows**, so a rejection frees the value for reuse and the table can end up holding duplicates: `clientes` two rows with one `rtn`, `lotes` two rows with one `nombre_lote` for a client. Note the two do it differently, and the difference is load-bearing: the `clientes` validators filter `isActive = 1`, but `validateNombreLoteDisponible` filters **`motivo_rechazo IS NULL`, not `estado`** — because spec 12 made a rejected lote `estado = 'cerrado'`, filtering on the state would also free the name of lotes closed with a *good* result once closing exists. `motivo_rechazo` is the only column written exclusively by the rejection.

Import path convention: absolute imports from `src/...` are used throughout (e.g. `src/decorators/public.decorator`) rather than relative `../../` paths, even for same-module files in some cases — follow existing files' style per-file rather than assuming one rule.

| `clientes` | `POST /clientes` (optional `usuario_ids` links operators), `GET /clientes` (only clients linked to the caller via `cliente_operador`), `GET /clientes/all` (spec 08; **every** active client, no `cliente_operador` filter, same six fields as `GET /clientes`; declared by `clientes.listar_todos` seeded for `Admin` only, but **not enforced** — any authenticated user, `Operador` included, gets 200 with the full list), `PATCH /clientes/:id/rechazar` (spec 11; **logical deactivation** of the client, not an approval flow — there is no `clientes.estado` column and `POST /clientes` still creates immediately-usable clients. Despite the name it is *not* "all lotes": it filters `estado = 'abierto'` too, so it hides rejected ones exactly like the other), `PATCH /lotes/:id/rechazar` (spec 12; **logical annulment** of the lote. Body is one required `motivo`, 5–255 chars. Responds `{ ok, msg }` with **no resource payload** — the third endpoint that returns nothing of what it touched, matching the other two `rechazar`. 400 if the lote does not exist, is not open (`estado != 'abierto'` or `cerrado_en != NULL`, which is also how "already rejected" is caught — there is no dedicated message for it), or if the `RECHAZADO` row is missing from `etapas`. Irreversible: nothing can undo it and no endpoint lists rejected lotes. **No cascade** — the lote's pesajes stay active, so `GET /pesajes/byLote/:loteId` still returns them while `POST /pesajes` and `PATCH /pesajes/:id/rechazar` both start returning 400, which makes those pesajes impossible to annul. **Frees the `nombre_lote`** for reuse in that client. **Does not check `cliente_operador` and has no `permisos` row** — see the auth notes) |

Body is one required `motivo`, 5–255 chars. Responds `{ ok, msg }` with **no resource payload** — the only endpoint that returns nothing of what it touched. 400 if the pesaje does not exist, is already rejected, has a null `lote_id`, or its lote is not open. | `permisos` | `GET /permisos/me` (spec 07; resolves `rol_id` from the JWT's `userId`, returns a flat `string[]` of the role's `permisos.codigo` where `isActive = 1`, unordered; 404 if the user no longer exists, `[]` if the role has none — **informational only, nothing is enforced**) |
| `catalogos` | `GET /catalogos/productos`, `GET /catalogos/usuarios`, `GET /catalogos/unidades-medida` (spec 09; read-only selector lists. Each returns `{ ok, msg, data }` where every element is exactly `{ id, nombre }` — **`data` is the payload key, not a named one**, the only three endpoints in the project that break the `{ ok, msg, <named payload> }` convention, by explicit decision. `productos` and `usuarios` filter `isActive = 1`; `unidades_medida` has no such column so it is unfiltered. `usuarios` aliases `complete_name as nombre` and returns **every** active user with no role filter and no `cliente_operador` filter. Ordered by `nombre` / `complete_name` ASC. No permission row is seeded for any of them — deliberately, see the auth notes) |

Beyond the `GET`s above and the three `PATCH`es of specs 10, 11 and 12, there is no `GET /clientes/:id`, no `GET /lotes/:id`, no `PUT` or `DELETE` anywhere, and no CRUD on the three catalog tables. Those three `rechazar` routes are the project's only non-`GET`/`POST` routes, its only three `UPDATE`s, and — with `GET /pesajes/byLote/:loteId` and the two `GET /lotes/cliente/:clienteId*` taking other param names — its only three `:id` path params. Deletion is always logical (`isActive = 0` on `pesajes`/`clientes`, `estado = 'cerrado'` on `lotes`); nothing issues a `DELETE FROM`. If `GET /clientes/:id` is ever added, declare it **after** `@Get('all')` in `ClientesController` or it will swallow `/clientes/all`; the same trap waits in `LotesController`, where a `GET /lotes/:id` declared before the two `cliente/...` routes would swallow both. Specs 11 and 12 each already put a `:id` in one of those controllers, on `PATCH`, which makes the mistake easier to make.

Every route Nest maps is now covered by a spec: `GET /pesajes/byLote/:loteId` was documented after the fact by spec 10, and `GET /lotes/cliente/:clienteId/all` by spec 12. Trust the route log over this table if the two ever disagree.

## Domain

This is a quality-control system for agricultural export batches. Core tables (see `src/database/types/types.ts`): `clientes` (clients/companies, with an `isActive` logical-deletion flag and — since spec 11 — the same rejection audit trio as `pesajes`: `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /clientes/:id/rechazar`), `cliente_operador` (many-to-many between clients and operator users), `lotes` (batches tied to a client + product, with `peso_minimo`/`peso_ideal`/`peso_maximo` tolerance range, an `etapa_id` pointing at `etapas`, an `estado`/`cerrado_en` lifecycle and — since spec 12 — the same rejection audit trio as `pesajes` and `clientes`: `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /lotes/:id/rechazar`), `etapas` (the stage of the flow a lote is in — `EN_PROCESO`, `CLIENTE_FINAL`, `RECHAZADO`, `FINALIZADO`, each with a `codigo` and a `nombre`; seeded by hand, no endpoint reads or writes it and **no spec designed it** — spec 12 only consumes the `RECHAZADO` row and left the rest, including `createLote`'s hardcoded `etapa_id: 1` = `EN_PROCESO`, for a future spec), `pesajes` (individual weigh-ins against a lote, with `peso_bruto`/`tara`/`peso_neto`, `fuera_de_rango`, and — since spec 10 — an `isActive` logical-deletion flag plus the rejection audit trio `motivo_rechazo`/`rechazado_por`/`rechazado_en`, all nullable, written only by `PATCH /pesajes/:id/rechazar`), `estados_calidad` (quality states applied to a pesaje), `productos`, `unidad_medida`, and `roles`/`usuarios` for auth, plus `permisos` (one row per `(rol_id, codigo)`, where `codigo` is `modulo.accion` — declared, **not enforced anywhere**; see the auth/guard notes above).

`diagram.jpeg` in the repo root is the intended end-to-end weighing flow and is the best reference for where the product is going. The backend currently implements only its happy path (capture weight → in range → save). **Not yet built, and needed by the diagram:** the *Etapa* concept — the `etapas` table and `lotes.etapa_id` exist and are seeded, but nothing drives a lote through the stages: `createLote` hardcodes `EN_PROCESO` and only `rechazarLote` ever changes the column, so `CLIENTE_FINAL` and `FINALIZADO` are never written — automatic derivation of the quality state (`APROBADO` / `APROBADO CON EXCEPCIÓN` / `RECHAZADO` — today `estado_calidad_id` comes from the request body and is only checked for existence), alert severity (today only a `fuera_de_rango` boolean, no yellow/red distinction), and supervisor PIN authorization for out-of-range weigh-ins at the final-client stage.

Also deferred by the existing specs, and worth knowing before proposing work: **closing a lote with a good result** — and read this carefully, because spec 12 changed the situation without implementing it. `rechazarLote` writes `estado = 'cerrado'` and `cerrado_en = NOW()`, so those columns are no longer untouched, but there is still **no** endpoint that closes a lote normally, no aggregates and no `resumen_ia`. The consequence to hold on to: **`estado = 'cerrado'` does not mean the lote finished well, and it does not mean closing exists** — today it only ever means "rejected". A rejected lote is identified by **`motivo_rechazo IS NOT NULL`**, never by its `estado`; `etapa_id` (`RECHAZADO` vs the future `FINALIZADO`) is a usable secondary signal. Whoever implements real closing inherits this: the value `'cerrado'` is already taken by rejections and the two will need telling apart. Also deferred: per-lote aggregates (total weight, counts by quality state), `resumen_ia` generation, batch/offline weigh-in sync and device idempotency by `(dispositivo_identificador, secuencia_dispositivo)`, and endpoints to manage `cliente_operador` links after a client is created.

MySQL decimal columns (`peso_*`) come back from the driver as `string | number`, and `pesajes.id` is a `BIGINT` typed as `Generated<string | number>` — coerce with `Number()` before comparing or returning.

## Caveats

- Any DDL is applied **by hand in MySQL**; there is no migration tooling and no `.sql` files in the repo. When a change needs schema work, document the DDL in the spec and update `src/database/types/types.ts` to match. (Specs 02 and 03 state "no DDL" as a decision — note that `pesajes.fuera_de_rango` was in fact added during spec 03, so that spec's acceptance criterion is inaccurate.) Specs 10, 11 and 12 are the only specs so far that declare their DDL up front, and they declare the same shape on three tables: three nullable columns (`motivo_rechazo VARCHAR(255)`, `rechazado_por INT`, `rechazado_en DATETIME`) on `pesajes`, then `clientes`, then `lotes`, each with a real FK from `rechazado_por` to `usuarios(id)`. The names are identical on purpose — it is the same operation on another table and the audit trail should read the same in all three. Those three FKs are the second, third and fourth exceptions to the application-code-only rule, after `permisos` → `roles`, justified as audit columns that would be worthless pointing at a missing user. Note the same inconsistency inside each table: `rechazado_por` has a FK while `pesajes.usuario_id`, `clientes.created_by` and `lotes.created_by` still do not. Spec 12 needed **no** DDL beyond that trio: `lotes.estado` is a plain `VARCHAR`, so writing `'cerrado'` did not require touching the column.
- `permisos` is seeded and maintained **by hand in SQL** — there is no CRUD endpoint (`GET /permisos/me` only reads) and nothing validates it at startup. Adding an endpoint means inserting its permission by hand, one row per role that should have it (`INSERT ... SELECT r.id, ... FROM roles r WHERE r.nombre = '<ROL>'`, resolving `rol_id` by name because role ids differ between environments). Nothing will warn you if you forget. There are five deliberate exceptions to that rule, so the rule has now gone unmet in four consecutive specs. Spec 07: `GET /permisos/me` has no permission row of its own, because requiring a permission to read your own permissions is circular. Spec 09: none of the three `catalogos` endpoints has one either — not circular, just a judgement call that reference lists everyone needs should not gate behind a permission nobody would be denied. Specs 10, 11 and 12: none of the three `rechazar` endpoints has one, which is the same judgement call applied to three destructive writes — see the auth notes. Spec 08 followed the rule and seeded one row, `clientes.listar_todos` for `Admin`, bringing the table to 11 rows (seven `Admin`, four `Operador`) — seeded but, like every other row, unenforced. Note also that `permisos` is the one place where uniqueness is enforced by real MySQL constraints (`UNIQUE (rol_id, codigo)` and a FK to `roles`), a deliberate exception to the application-code-only rule above, precisely because no application code writes to this table.
- `README.md` is still the stock NestJS boilerplate; there is no Swagger/OpenAPI setup, so `specs/` plus this file are the API documentation.
- `dist/` is present in the working tree.
